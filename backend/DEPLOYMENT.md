# NexusPlay API — Render deployment

The API is an ASP.NET Core 10 application. Deploy it as a separate Render **Web Service** using the Dockerfile in this directory. The frontend remains a Render Static Site.

## 1. Create the API service

In Render, create **New → Web Service**, connect this repository and select the backend-hardening branch or the merged main branch.

Use these settings:

| Setting | Value |
|---|---|
| Runtime | Docker |
| Branch | `fix/backend-production-hardening` (or `main` after merge) |
| Root Directory | `backend` |
| Dockerfile Path | `Dockerfile` |
| Health Check Path | `/health` |
| Port | `10000` (the container also reads Render's `PORT`) |

Choose the same Render region as any managed database where practical.

## 2. Required API environment variables

Add these in the API service's Environment page. Do not put secret values in GitHub, this document, Docker build arguments, or the frontend.

| Key | Value / guidance |
|---|---|
| `ASPNETCORE_ENVIRONMENT` | `Production` |
| `Mongo__ConnectionString` | Private/secure MongoDB connection string |
| `Mongo__Database` | `nexusplay` |
| `Jwt__Secret` | Random secret, at least 32 bytes (example generator: `openssl rand -base64 48`) |
| `Jwt__Issuer` | `nexusplay` |
| `Jwt__Audience` | `nexusplay-app` |
| `Jwt__ExpiryMinutes` | `10080` |
| `Cors__Origins__0` | `https://nexusplay1830.onrender.com` |
| `App__PublicUrl` | API origin, e.g. `https://YOUR-API-SERVICE.onrender.com` (no trailing slash) |
| `App__FrontendUrl` | `https://nexusplay1830.onrender.com` (no trailing slash) |
| `Admin__Email` | Initial admin email |
| `Admin__Password` | Initial admin password, at least 12 characters |

The first admin is created only when the MongoDB users collection is empty. Changing these seed variables later does not reset an existing admin password.

For additional frontend origins, add `Cors__Origins__1`, `Cors__Origins__2`, etc. Never use a wildcard origin with credentials.

## 3. SSLCOMMERZ

Start in sandbox mode and test a complete order before accepting live payments.

| Key | Initial/test value |
|---|---|
| `SslCommerz__Mode` | `sandbox` |
| `SslCommerz__StoreId` | Your sandbox Store ID |
| `SslCommerz__StorePassword` | Your sandbox Store Password |

For live payments, use the production merchant credentials and set `SslCommerz__Mode=live`. Never put either credential in frontend variables.

Configure the merchant portal IPN Listener URL as:

`https://YOUR-API-SERVICE.onrender.com/api/payments/webhook`

The success and fail callback URLs are generated by the API using `App__PublicUrl`; the customer is then redirected to the frontend using `App__FrontendUrl`.

Card checkout requires a valid customer email (maximum 50 characters), as required by the gateway integration. Stripe is not enabled; SSLCOMMERZ is the only implemented card gateway.

## 4. Frontend Static Site environment

In the existing frontend Static Site, set this build-time variable:

`VITE_API_URL=https://YOUR-API-SERVICE.onrender.com/api`

Save and rebuild the static site after setting it. The value must end in `/api`; frontend calls append routes such as `/auth/login`, `/orders`, and `/payments/initiate`.

## 5. Optional notifications

Email is skipped safely unless configured:

- `Email__Smtp__Host`
- `Email__Smtp__Port` (usually `587`)
- `Email__Smtp__User`
- `Email__Smtp__Password`
- `Email__From__Address`
- `Email__From__Name` (optional, defaults to NexusPlay)

SMS is disabled by default:

- `Sms__Provider=disabled`

To enable the implemented Twilio adapter, set `Sms__Provider=twilio`, `Sms__AccountSid`, `Sms__AuthToken`, and `Sms__From`. The Twilio sender must be authorised for the destination numbers.

## 6. Product image persistence

Render services have an ephemeral filesystem by default. Uploaded product images can disappear after a redeploy unless they are stored on a persistent disk or external object storage.

For the current local-upload implementation:

1. Attach a persistent disk to the API service, mounted at `/var/data`.
2. Set `Storage__UploadsPath=/var/data/uploads/products`.
3. Keep the API on a single instance while using that disk.

This maps the persisted files to `/uploads/products/... `. A cloud object-storage service is the better long-term option when horizontal scaling is required.

## 7. Verify after deployment

1. Open `https://YOUR-API-SERVICE.onrender.com/health`; it should return `{"status":"healthy"}`.
2. Check the API service logs for successful startup and MongoDB index initialization.
3. Check that the frontend can load products and call the API without CORS errors.
4. Test account registration/login and authenticated wishlist/admin endpoints.
5. Test COD and manual bKash order creation.
6. Test SSLCOMMERZ sandbox success, cancel/fail, duplicate IPN delivery, amount mismatch, and a high-risk transaction. Confirm that only validated, matching, low-risk transactions become paid.
7. Test product image upload, redeploy the API, and verify uploaded images remain available.

Before applying this to an existing production database, review the startup log for duplicate legacy order numbers. The API skips creating its unique order-number index when duplicates already exist, so those records can be reconciled separately without blocking service startup.
